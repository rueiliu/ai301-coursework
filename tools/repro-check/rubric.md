# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `env-recorded` | The environment record in the repro report (the `Environment:` line or equivalent), read against the version, platform and build the issue and its repo-facts block name as the target. | The report names both (1) the exact build of the software under test (release version, tag, or commit) and (2) the platform it ran on (OS, and any runtime, driver or profile the issue's failure depends on). If that build differs from the one the issue targets, the report says so and says why. An environment that is absent, or that silently differs from the issue's target, fails. | required |
| `steps-followable` | The reproduction steps in the repro report, read as a stranger with no access to the author's machine. | A stranger could re-run the attempt from the steps alone: the starting state is one they can reach (a public clone, a released artifact, or an input included verbatim in the package), and the trigger is given as the exact command, input or action, not a description of one. Steps that depend on a private repository, an unshared config or fixture, or an unnamed setting the failure needs, fail. | required |
| `behavior-matches` | The artifacts in the repro report (output excerpts, logs, exit codes, screenshots) read side by side with the failure the issue's own text and artifacts describe, and the input each was produced from. | One of two things holds. (1) The report claims a reproduction, and the artifact shows the same failure the issue describes — the same error, exit code, or symptom class — produced by the input the issue names. A graceful error standing in for a crash, a compile error standing in for a runtime error, a different exit code, or a different input than the issue's, all fail here however confidently the surrounding text narrates them. (2) The report states it could not reproduce, and the artifact shows a genuine attempt at the trigger the issue names, with the report claiming no more than that. | required |
| `outcome-honest` | Every factual claim the claim comment and the repro report make (reproduced / not reproduced, root cause, certainty words such as "guaranteed", "verified", "confirmed"), read against what the package actually shows. | Each claim is backed by something shown in the package. A stated reproduction has an artifact of the failing run; a stated root cause has the observation that supports it; a stated certainty has the run behind it. The report's own "expected" and "actual" describe what the artifact shows, not what the author assumed. A report with no artifact at all, or one whose artifacts show only that the software runs, fails. An explicit, evidenced "I could not reproduce this" passes: reporting that faithfully is an honest outcome, not a failure. | required |
| `comms-conventions` | The claim comment and repro comment read against the repo-facts block: the repo's stated contribution and AI policy, and its bug-report template asks. Course packages are AI-assisted work, so any disclosure duty applies. | Both hold. (1) Policy: if the repo's stated policy requires disclosing AI assistance, the comments disclose it and say what the assistance was. A policy that is silent, or that only asks the contributor to understand and take responsibility for the work, or that asks comments be written by a human in their own words, imposes no disclosure duty and passes without one. (2) Claim: the claim comment names this issue's specifics — the version, behavior, or file at stake — so it could not be pasted onto another issue, and it promises only investigation or a report. A promise of a fix, a delivery date, or an interchangeable "please assign me" fails. | required |
| `control-run` | The repro report's artifacts, looking for a second run alongside the failing one. | The report shows a contrasting run — the working case, the pre-condition, or the same command with the triggering element removed — so the difference the issue describes is visible rather than asserted. | preferred |
| `next-step-named` | The closing of the claim comment or repro report. | The author names a concrete next action they will take (a specific file, function, or hypothesis to examine), rather than ending with a general offer to help. | preferred |

## Verdict rule

Accept (ready to post) only if every `required` check passes. A single
`required` fail holds the package. `unclear` on a `required` check counts as
a fail: proof I cannot verify is proof that is not ready to post. The one
exception is the claim-only draft state, where the checks whose evidence is
the repro report are reported `unclear` as "not yet applicable" and left out
of the verdict entirely, so the verdict answers only whether the claim
comment is ready. `preferred` checks never change the verdict; they separate
a package that is merely ready from one that is genuinely easy to act on.
